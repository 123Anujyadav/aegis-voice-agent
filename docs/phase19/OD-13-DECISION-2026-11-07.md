# Owner decision OD-13: recovering a corrupt session file (2026-11-07)

- **Decision:** approved by the owner on 2026-11-07, on the read-only technical review of the same day.
- **Decision ID:** OD-13 ([`ROADMAP-INVENTORY.md`](ROADMAP-INVENTORY.md) §3.3), for production-readiness finding **F3** ([`PRODUCTION-READINESS.md`](PRODUCTION-READINESS.md) §4, §4.1).
- **Class:** O, an owner decision. It is not high-risk, so it needs no independent review (OD-12).
- **Implemented in:** #258.

## The problem (F3)

The Android app keeps the encrypted session in one Preferences DataStore file (`callscreen_identity_session`). That DataStore had **no corruption handler**. If the file stopped being valid Preferences data:
- every read and every write of it failed with `CorruptionException`;
- the app started at onboarding without crashing (the splash's guard, #202);
- but signing in could never store a session: identity enrolled the phone, and the app then answered "storage failed", on every attempt.

## The decision

**An unparseable session DataStore file is replaced with an empty file.**

**The owner accepted these consequences:**
- **The user is signed out** and must enrol, that is sign in, again.
- **The previous server-side session may remain active until its fixed 24-hour expiry.** Identity has no sign-out route, and the phone no longer holds its tokens.
- **The user-facing signed-out behaviour is unchanged:** there is **no new corruption notice**. The app starts at onboarding, as it already did with a corrupt file.

## What changes, and what does not

**Changes:**
- **`AndroidSessionStorage.kt`:** the session DataStore's delegate gets `sessionStoreCorruptionHandler()`, a `ReplaceFileCorruptionHandler` that returns `emptyPreferences()`. This is the only production change.
- **Afterwards:** the store reads as Absent, the session state is "not signed in", and a new sign-in stores its session in the replaced file.

**Unchanged:**
- **Other failures:**
  - a file that parses but holds a record that cannot be opened still takes the existing Unrecoverable path (`EncryptedSessionStore`);
  - other I/O errors still fail as before.
- **Code not touched:**
  - `SessionStore.kt`, `IdentityAuthenticator.kt` and `IdentityModule.kt`;
  - the AES-256-GCM sealing and its key;
  - the DPoP device key;
  - token refresh and rotation;
  - sign-out and account deletion;
  - the server, its sessions and its API.
- **Not recovered:** the record inside a file that does not parse may itself be intact. It is not salvaged.

## Tests (#258)

**`SessionStoreCorruptionTest`** (`:core:datastore`, real DataStore files on the JVM):

| Test | Checks |
|---|---|
| A0 | **Control:** without the handler, every corrupt file fails every read and write |
| A1 | Corrupt files recover to empty and are rewritten as valid files. Three kinds: an invalid tag, random bytes, and a truncated record |
| A2 | A missing file is the normal empty state, and reading creates nothing |
| A3 | A valid file is left byte-for-byte unchanged |
| A4 | A new session persists after recovery |
| A5 | Repeated reads neither fail nor rewrite the file |
| A6 | An I/O error that is not corruption still fails, and nothing is replaced |

**`SessionFileCorruptionTest`** (`:app`, Robolectric, the app's real delegate and `DataStoreBlobStore` under the authenticator):

| Test | Checks |
|---|---|
| B1 | A corrupt file reads as Absent and is replaced; no key is touched |
| B2 | After a corrupt file: onboarding, "not signed in", nothing sent; then exactly one enrolment reaches identity and the session is stored and found at the next launch |
| B3 | A missing file is the normal absent session |

**Mutation checks:**
- With the handler rethrowing instead of recovering, A1, A4, A5, B1 and B2 fail.
- With no handler on the delegate, B1 and B2 fail.
