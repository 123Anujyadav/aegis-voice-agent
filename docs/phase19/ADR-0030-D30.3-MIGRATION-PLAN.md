## 2. Requirements and where each is validated

### 2.1 Existing subscribers keep their ids

**Rule.** Legacy-preserving adoption: the first mapping for a number stores
today's derived id.

**Validated by:**
- `TestLegacySubscriberID_IsUnchanged` (the golden value, computed
  independently);
- `TestDirectory_AdoptsTheLegacyID`;
- `TestMigration_StageOneChangesNothing`.

### 2.2 Compatibility

- A random id has exactly the legacy shape: `usr_` and 32 lowercase hex
  characters. No consumer can tell the two apart.
- Stage 1 reads a mapping if one exists, otherwise derives as today, and
  writes nothing.

**Validated by:** `TestMigration_ReadsPerStage` and
`TestMigration_StageOneChangesNothing`.

### 2.3 Dormant subscribers

A dormant subscriber has live sessions but never re-verifies, so they never
get a mapping row.

**What the code provides:** `DormantSubscribers(sessionIDs, rows)` lists them.
This list is:
- the count that blocks retirement;
- the set of rows that the `NOT VALID` foreign key from sessions must
  tolerate.

**The consequence:** after retirement, a dormant subscriber who comes back
gets a **new id**. An active subscriber keeps theirs. The owner must accept
this as a product decision.

**Validated by:** `TestMigration_DormantSubscribersAtRetirement`.

### 2.4 Collisions and concurrency

- **Random ids** have 128 bits.
  - The chance of any collision among N ids is about N² / 2¹²⁹. For 10⁸
    subscribers that is about 10⁻²³.
  - A collision is retried 3 times, and then fails closed.
- **Two numbers deriving the same legacy id** is refused, not shared.
- **Two first enrolments of one number at the same time** get one id.

**Validated by:** `TestDirectory_CollisionsRetryThenFailClosed` and
`TestDirectory_ConcurrentFirstResolutionsAgree`.

### 2.5 Backups, rollback and recovery

See §4.

**Validated by:**
- `TestMigration_BackupRestoreIsLossless`;
- `TestMigration_RestoringAnOlderBackup`;
- `TestMigration_StageTransitions`;
- `TestMigration_InvariantsRefuseCorruptMappings`.

### 2.6 Rotating the HMAC keys

See §5.

**Validated by:**
- `TestMigration_PseudonymKeyRotationNeverChangesAnID`;
- `TestMigration_DroppingAnOldSubscriberKeyStrandsRows` (the hazard);
- `TestMigration_KeyringLookup*` (the mitigation).

### 2.7 Auditability

See §6. This is design only: the event lands when the directory is wired in.

### 2.8 Privacy

- A backup row holds a pseudonym, an id and an origin. It never holds a
  number.
- A number-shaped value in either field is refused by the invariant check.

**Validated by:** `TestMigration_BackupRestoreIsLossless` and
`TestMigration_InvariantsRefuseCorruptMappings`.

## 3. Schema: one amendment to D30.5's table

D30.5 proposes this table:

```
identity_subscribers(subscriber_pseudonym PK, key_id, subscriber_id UNIQUE, created_at)
```

**This plan adds `id_origin`, which is either `legacy` or `random`:**

```
identity_subscribers(
  subscriber_pseudonym  text PRIMARY KEY,   -- 64 lowercase hex
  key_id                text NOT NULL,      -- the subscriber key that made the pseudonym
  subscriber_id         text NOT NULL UNIQUE,
  id_origin             text NOT NULL CHECK (id_origin IN ('legacy','random')),
  created_at            timestamptz NOT NULL
)
```

**Why the column is needed:**
- D30.5 allows a rollback to stage 0 only "while every row holds a legacy id".
- A row's origin **cannot be worked out afterwards**: the number is never
  stored, so the legacy id cannot be recomputed and compared.
- Without the column, the stage 2 → 0 guard cannot be checked.

**Where it is modelled:** `SubscriberIDOrigin` holds it, and the
`stage0 origin guard` mutation shows that the guard depends on it.

**It needs the owner's sign-off** together with D30.3, because it changes
D30.5's table.

**The table has CHECK constraints in the style of `0005_security_audit`:**
- the pseudonym is `^[0-9a-f]{64}$`;
- the id is `^usr_[0-9a-f]{32}$`.

The same rules are applied in code by `CheckSubscriberMappings`.

## 4. Stages, preconditions and rollback

`CheckStageTransition` encodes these rules, and each one is mutation-checked.

| Move | Allowed when | Refused when |
|---|---|---|
| Forward, one stage at a time | The legacy key is held | Skipping a stage (`0 → 2`) |
| `0 → 1`, `1 → 2`, `2 → 3` | The legacy key is held | The legacy key is not held |
| `3 → 4` (retire the legacy key) | The owner has accepted that dormant subscribers get new ids, **and** `DormantSubscribers(...)` is empty | Either condition is missing |
| `2 → 1` | Always (stage 1 reads the rows) | — |
| `3 → 2` | The legacy key is still held | The legacy key is not held |
| `→ 0` | **Every row is `legacy`** | Any random id exists: stage 0 would silently replace it |
| From 4 | — | **Always.** Retirement cannot be undone. |

A directory that fails `CheckSubscriberMappings` blocks every move.

### Backup and recovery

**Before stage 2:** there are no rows, so there is nothing to back up.

**Stages 2 and 3:** `identity_subscribers` must be backed up with the rest of
the identity database (point-in-time recovery). Restoring a backup:
- uses `RestoreMemorySubscriberDirectory`, which refuses a corrupt backup as a
  whole and never restores part of it;
- loses nothing when the backup is complete.

**Restoring an older backup** depends on the stage the rows were written in:
- **Rows written in stage 2: no loss.** A lost row is re-adopted with the same
  legacy id at the subscriber's next verification.
- **Rows written in stage 3 or later: the ids are lost.** A lost random id
  cannot be recovered, and the subscriber gets a new one.

**So, from stage 3 on, backups are a correctness requirement, not just
hygiene.** SRE must confirm point-in-time recovery for the identity database
before `2 → 3`.

**Stage 4 removes the safety net that stage 2 had:** without the legacy key, a
lost row can no longer be re-derived.

## 5. Rotating the HMAC keys

**Rotating the subscriber-pseudonym key never changes an id:**
- When a subscriber verifies, the mapping moves from the old pseudonym to the
  new one (`Rekey`), keeping its id and origin.
- A retry is a no-op.
- A move onto a pseudonym that maps to a different id is refused, and nothing
  changes.

**A new hazard that D30.3 does not state.** D30.3 says the subscriber key is
"rotated lazily, as in D30.2". D30.2's rule, that the previous key can be
removed once a short window has passed, **is not safe for this key**:
1. The state D30.2 covers lasts minutes. Mapping rows last forever.
2. A row can only be re-keyed when its subscriber verifies, because the number
   is needed to compute the new pseudonym.
3. If the old key is dropped, every dormant subscriber's row is **stranded**.
4. When a stranded subscriber comes back, legacy adoption under the new key
   tries to store the id the stranded row already holds. **The UNIQUE
   constraint refuses it, and the subscriber is locked out (fail closed).**

`TestMigration_DroppingAnOldSubscriberKeyStrandsRows` pins this.

**Recommendation, for the owner to adopt with D30.3:**
- **Lookups use the whole subscriber keyring;** new pseudonyms use only the
  active key. This is modelled by `ResolveWithKeyring` and checked by
  `TestMigration_KeyringLookupKeepsDormantSubscribersAcrossRotations`: a
  dormant subscriber keeps their id across two rotations, and their row moves
  to the active key. Concurrent returns agree on one id.
  - A key leaves the lookup ring only once `count(rows WHERE key_id = k) = 0`.
  - With dormant subscribers, that may be never.
  - The cost is one HMAC per retained key on each verification.
- **Why keeping old keys is acceptable:** someone holding an old subscriber
  key can only test whether a given number is registered, and only if they
  can also read the table. It reveals no number.
- **If an old key is compromised:** stop creating new pseudonyms with it
  (already the case for any non-active key). Keep it for lookups. Remove it
  only with the same owner-accepted reassignment as retirement in §4.

**The legacy key's two roles** (adoption, and checking hashes from before the
split) are covered by the `3 → 4` rule above.

## 6. Auditability

**Mapping creation** emits `identity.subscriber.created` through the existing
security auditor:
- it is written to the append-only `identity_security_audit` log and counted
  in `identity_security_events_total{type}`;
- it carries **no identifier**. The audit schema's CHECK constraints already
  admit only request and session ids;
- this lands when the directory is wired in, not in this PR.

**Re-keying** is not audited per row: it is routine and frequent. It is
counted by a metric instead.

**Stage changes** are operational events:
- each one is recorded in the change log with the operator, the time and the
  `CheckStageTransition` inputs (whether the legacy key is held, whether the
  owner decided, and the dormant count);
- `3 → 4` needs the owner's written decision to be linked.

## 7. What execution still needs, in order

1. **The owner decides D30.3**, together with the `id_origin` amendment (§3)
   and the subscriber-ring rule (§5).
2. **A PostgreSQL implementation:**
   - a migration `00NN_identity_subscribers` (forward only), plus a
     `pgstore.SubscriberDirectory` that matches the memory reference;
   - real-PostgreSQL tests (the identity-postgres CI job) for every case
     above, plus: concurrent first enrolment through
     `INSERT … ON CONFLICT DO NOTHING` then `SELECT`; the foreign key added
     `NOT VALID` and validated only once `DormantSubscribers` is empty; and
     requesting a code creating no row.
3. **Wiring:**
   - the challenge stores a subscriber pseudonym instead of an id;
   - the id is resolved after verification;
   - stages are selected by configuration, defaulting to stage 0;
   - the audit event from §6.
4. **SRE:**
   - provision the per-purpose keys (D30.1);
   - confirm point-in-time recovery before `2 → 3`.
5. **Run each stage in staging, then in production**, one stage per change,
   with `CheckStageTransition` inputs recorded each time.
6. **Stage 4 only on the owner's retirement decision.**

**None of steps 2–6 is authorised by this document.**
