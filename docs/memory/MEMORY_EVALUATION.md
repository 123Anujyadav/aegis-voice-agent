# Memory Evaluation Report — Enterprise Memory Engine

**Phase 10C** · `packages/go/memory` · 2026-08

An engineering audit asks *is this built correctly*. This report asks a
different question: **does this engine remember and forget the right things?**

Every figure below is produced by
[`eval_test.go`](../../packages/go/memory/eval_test.go) and reproducible with:

```
cd packages/go/memory
go test -run TestEvaluation -v .
```

The suite measures **and asserts**. A report generated by tests that cannot fail
is a press release.

---

## 1 · What can and cannot be evaluated in this phase

**Can be:** whether a stored memory is recalled; whether a scope leaks; whether
the tier a memory occupies is explained by a rule; whether erasure leaves
anything reachable; whether retention fires at the right time; what survives a
starved context budget; whether identical inputs produce identical memory.

**Cannot be:** summary quality, semantic recall, anything needing a model. The
brief excludes summarisation, embeddings and semantic search, so there is no
similarity metric to report. **A recall@k here would be measuring a retrieval
mechanism this engine does not have.**

Every number below is a *deterministic* measure over a fixed corpus, not a
statistical estimate over a sample. There is no variance to report because
§E7 establishes there is no randomness in the system.

---

## 2 · Corpora

Built with `FakeClock`, so a 90-day retention window is exercised in
microseconds.

| Scenario | Shape | Records |
|---|---|---:|
| **S1 · Single screening call** | 1 policy, 3 preferences, 24 conversation turns on one conversation | 28 |
| **S2 · Returning caller** | 8 preferences, 5 conversations × 4 turns over 30 days, 12 contacts | 40 |
| **S3 · Business receptionist** | 2 policies, 6 business records, 8 preferences, 40 conversation turns | 56 |

Plus derived corpora for multi-namespace erasure (S2 + fraud + telephony +
receptionist + a legal hold = 44) and per-retention-class probes.

## 3 · Results

### E1 · Recall of what was stored

**Question:** is every stored, active, in-scope record returned by a scoped
query for it?

```
S1 single call         stored=28 recalled=28 recall=100.0%
S2 returning caller    stored=40 recalled=40 recall=100.0%
S3 business            stored=56 recalled=56 recall=100.0%
```

**100%, and it must be.** This is an exact-match index, not a ranking system —
a miss here is an index bug, not a quality shortfall. That is exactly what makes
the number valuable as a regression guard and uninteresting on its own.

The evaluation that matters is not *whether* a record is found but **what
happens when it should not be** — E2 and E4.

*`TestEvaluation_RecallIsTotal`*

### E2 · Precision of scoping

**Question:** does any query ever return a record outside its scope?

```
subject A query returns subject B                returned= 29 leaks=0
conversation 1 query returns conversation 2      returned= 24 leaks=0
Internal ceiling returns Personal                returned= 29 leaks=0
active query returns non-active records          returned= 29 leaks=0
assistant reads fraud namespace by key           leaks=0
TOTAL LEAKS ACROSS ALL PROBES: 0
```

**Zero across every probe.** Note the corpus was built adversarially: two
subjects with identical record names, two conversations, a Personal record above
the ceiling, an expired scratchpad, and the same subject present in the fraud
namespace.

The namespace probe is by **key, not query** — isolation is structural, so the
fraud record simply is not in the assistant's store. A permission check can be
misconfigured; a separate store cannot.

*`TestEvaluation_ScopeNeverLeaks`*

### E3 · Promotion justification

**Question:** for every tier a record occupies, does a stated rule explain it?

The test predicts each decision from `PromotionPolicy.Evaluate` *before* the
sweep, then compares against what the sweep did. A divergence would mean the
sweep promotes for reasons the policy cannot explain.

```
predicted promotions=12 actual=12
tier distribution: working=20 short=0 long=20
promotions with no explaining rule: 0
```

Reading the distribution on S2 (40 records):

| Tier | Records | Content | Rule |
|---|---:|---|---|
| Long-term | 20 | 8 preferences + 12 contacts | Preferences pinned at creation; contacts read 3× past the 5 s minimum age |
| Working | 20 | 20 conversation turns | Idle past `IdleToDemote`, demoted |

**Prediction matched reality exactly.** That is the property behind *"why does
it remember that about me"* being answerable: `Evaluate` is a pure function of
record, policy and instant, so the explanation can be recomputed at any time
from state that is still there.

**Derived memories:** 4 created, deliberately read 30 times across 10 sweeps.

```
derived records created=4 reached long term=0
```

**Zero.** An inferred memory promoted to permanence would be the platform
deciding, on its own, to permanently remember something a person never said.

*`TestEvaluation_EveryPromotionIsExplained`,
`TestEvaluation_DerivedNeverClimbsToLongTerm`*

### E4 · Forgetting correctness

**Question:** after an erasure, is anything about the subject still reachable —
by key, by attribute, by subject scan, in any namespace?

44 records across all four namespaces, one under legal hold:

```
stored=44 deleted=43 redacted=1 retained=0 complete=false
after erasure: readable payloads=0 reachable by key=0 reachable by attribute=0
records still present (redacted shells)=1 namespaces missed=0
legal-hold survivor named in the report: true
```

| Route back to the data | Result |
|---|---|
| Primary key retrieve | **0** — tombstones only |
| Secondary index by attribute | **0** — index entries removed |
| Subject scan | 1 redacted shell, existence only, zero payload |
| Namespaces not visited | **0 of 4** |

**`Complete: false` is the important field.** One record survived under legal
hold, so the report does not claim completeness — and it *names* the survivor
rather than counting it. A subject exercising an erasure right learns exactly
what was kept.

An erasure that silently retained would score identically on every other row
here and be a compliance failure.

*`TestEvaluation_ErasureLeavesNothingReachable`*

### E5 · Retention accuracy

**Question:** does expiry fire at the horizon — never before it?

The probe reads each record immediately before the pre-horizon sweep, which
resets idleness. Without that, the sweep's idle-demotion path would expire the
record for an unrelated reason and the measurement would be of **disuse, not
retention**.

```
short        configured=24h0m0s   early=false state_after=expired
standard     configured=2160h0m0s early=false state_after=expired
legal hold   configured=never    expires_at=zero(true) state after 365d=active
```

| Class | Horizon | One second early | One second late |
|---|---|---|---|
| Short | 24 h | **Active** | Expired |
| Standard | **2,160 h = 90 days** | **Active** | Expired |
| Legal hold | none — `ExpiresAt` is the zero time | Active after 365 days | — |

**Never early.** Retention is a *maximum*, so lag bounded by the 30 s sweep
interval is correct and undershooting by anything would be data destroyed before
it was allowed to be.

The 90-day standard horizon is confirmed as matching ADR-0012's transcript
window rather than being chosen independently. **Legal hold has no duration at
all**, not a very long one — giving it one is how the records that must be kept
get accidentally deleted.

*`TestEvaluation_RetentionIsNeverEarly`*

### E6 · Context quality under budget pressure

S3 starved to 25% of demand:

```
demand=855 tokens  budget=213 tokens (25%)  used=207  unused=6
  kept    runtime        records= 2 tokens=  16 truncated=false
  kept    personal       records= 8 tokens=  32 truncated=false
  kept    business       records= 6 tokens= 132 truncated=false
  kept    conversation   records= 1 tokens=  27 truncated=true
```

| Priority | Scope | Demanded | Included | Whole? |
|---:|---|---:|---:|---|
| 0 | Runtime (2 policies) | 2 | 2 | **Yes** |
| 1 | Personal (8 preferences) | 8 | 8 | **Yes** |
| 2 | Business (6 records) | 6 | 6 | **Yes** |
| 3 | Conversation (40 turns) | 40 | **1** | **No — truncated** |

**The measured property is not how much fitted but what was sacrificed.** At a
quarter of the budget, every operating limit, every preference and every
business record survived whole; conversation history absorbed the entire cut.

That is the intended ordering: an assistant that forgets an operating limit is
**dangerous**, one that forgets a stated preference is **rude**, one that
forgets the last few exchanges is merely **forgetful**. Under pressure the
engine chose the forgetful failure.

**Truncation is permitted; silence about it is not.** The conversation slice
reports `Truncated: true` and `Available: 40`, so a caller can tell a short
context from a complete one and decide whether to re-request with a larger
budget. The asserted rule is stricter for the top two scopes: **runtime and
personal must never be truncated** — a context confidently wrong about the
subject is worse than one visibly short of history.

Six tokens went unused: the next conversation turn did not fit, and a scope
stops at the first record it cannot afford rather than skipping ahead to find a
smaller one. Cheating the budget by reordering would produce a context whose
contents depend on payload size rather than on relevance.

*`TestEvaluation_ContextKeepsWhatMatters`*

### E7 · Determinism

**Question:** does the same corpus produce the same memory twice?

25 independent runs of build → read → sweep → search → assemble context:

```
runs=25 sweep divergences=0 search divergences=0 context divergences=0
```

**Zero across all three fingerprints.** Sweep decisions and their order, search
result ordering, and the exact contents of an assembled context are byte-stable.

This is not a nicety. A memory system that produces different results on
identical inputs cannot be debugged from a bug report, cannot be audited, and
cannot answer a regulator asking what it held on a given date.

*`TestEvaluation_IdenticalInputsProduceIdenticalMemory`*

### E8 · Behaviour under concurrency

From the stress suite — 8 readers, 4 writers, sweeper running, at
`-count=3 -shuffle=on`:

| Check | Result |
|---|---|
| Torn reads observed | 0 |
| Lost updates (CAS violations) | 0 |
| Deadlocks | 0 |
| Panics | 0 |

**Caveat, and a real one:** never run under `-race` (ENGINEERING_AUDIT §A2).
*No anomaly was observed* is the honest claim; *there are no data races* is not
available.

*`TestStress_ConcurrentReadWriteSweep`, `TestStress_ConcurrentUpdatesToOneRecord`,
`TestStress_ConcurrentWritesAcrossSubjects`, `TestStress_ManyNamespacesConcurrently`*

### E9 · Failure behaviour

| Injected failure | Behaviour | Test |
|---|---|---|
| Summariser fails | Inputs untouched, no summary written | `TestIntegration_FailedSummarisationLeavesInputsIntact` |
| Encryptor fails on store | Write refused, nothing indexed | `TestFailure_EncryptorFailureRefusesTheWrite` |
| Publisher fails | Counted, write proceeds | `TestEvents_FailingPublisherDoesNotFailTheWrite` |
| Auditor absent, Sensitive read | **Refuses to start** | `TestPolicy_RequireAuditorRefusesToStartBlind` |
| CAS conflict | `ConflictError` with both versions | `TestConsistency_StaleWriteIsRefused` |
| Sweep budget exhausted | Partial pass, reported, resumes | `TestLoad_SweepStaysWithinBudget` |
| Merge input missing | Whole merge refused, no partial state | `TestIntegration_MergeIsAllOrNothing` |

**The compression case is the important one.** A summariser failure that had
deleted the inputs would destroy a conversation's history in exchange for
nothing — the single most damaging failure this engine could have. It is
all-or-nothing and tested as such.

## 4 · What the engine is deliberately bad at

An evaluation listing only strengths is not an evaluation.

| Weakness | Consequence | Deliberate? |
|---|---|---|
| **No semantic recall** | "What did they say about the delivery?" is unanswerable unless a caller stored it under a matching key or attribute | Yes — brief excludes it |
| **No summarisation** | Long conversations accumulate turn records; compression selects but cannot condense | Yes — brief excludes it |
| **Conversation history is the first thing cut** | E6: at 25% budget, 39 of 40 turns were dropped | Yes — and the right choice, but it is a real limit |
| **Subject scan is O(n)** | Erasure and access requests cost ~30 ns/record | Yes — PERFORMANCE §2 |
| **Nothing is inferred** | A memory joins a conversation only because a caller said so | Yes — inference means parsing payloads |
| **No cross-namespace recall** | The receptionist cannot use what the assistant learned | Yes — isolation is the point |
| **No authorisation** | Any in-process consumer reads anything in its namespace | Accepted — SECURITY_REVIEW R3 |
| **In-memory only** | Process restart loses everything | Yes — persistence is Phase 10D |

**The first two will be felt.** This engine remembers precisely and recalls
literally. It is the right foundation for both improvements — the `Summarizer`
seam and the attribute index are where each attaches — but adding them is a
product decision, not a gap to be filled quietly.

**The third is worth watching in production.** E6 shows conversation history
absorbing the entire budget cut. That is correct prioritisation, but a
deployment whose budgets are routinely this tight will have an assistant that
knows the subject well and remembers the current call badly. The fix is a real
summariser, which is exactly what the compression framework was built to accept.

## 6 · Assessment

Measured, not asserted: recall is total across three corpora; scoping leaked
zero records across five adversarial probes; every promotion was predicted
before it happened; erasure left zero payloads, zero retrievable records and
zero index entries across four namespaces while correctly refusing to claim
completeness; retention never fired early; a context starved to a quarter of its
budget kept every operating limit and every preference whole; and 25 identical
runs produced 25 identical memories.

Its limits are the ones the brief drew — it recalls literally and condenses
nothing — and both have a named interface waiting.

The gap between this and a production memory layer is **persistence, encryption
and a race-verified concurrency story**, not correctness of the model.
